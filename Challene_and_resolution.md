# EventFlow — Challenges, Bugs & Resolutions

Real problems encountered during development, with root cause analysis and fixes applied.
These are documented for interview preparation — every item below was actually debugged and resolved.

---

## 1. ESM + TypeScript Import Resolution — `ERR_MODULE_NOT_FOUND` at Runtime

**Symptom:**

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '/app/app/api/dist/middleware/adminAuth'
imported from /app/app/api/dist/routes/admin.route.js
```

**Root cause:**
The project uses `"type": "module"` (ESM) throughout. Node's ESM resolver does not do automatic extension resolution like CommonJS did — it resolves imports literally. TypeScript compiles `import ... from "../middleware/adminAuth"` into the output `.js` file with the same literal string. At runtime, Node cannot find `adminAuth` (no extension) and crashes.

**Fix:**
Every relative import in TypeScript source files must include the `.js` extension explicitly, even though the source file is `.ts`:

```typescript
import { adminAuthMiddleware } from "../middleware/adminAuth.js";  // correct
import { adminAuthMiddleware } from "../middleware/adminAuth";     // breaks in ESM
```

**Lesson:**
In ESM + TypeScript projects, `.js` extensions in imports are mandatory. `tsx` (used in dev) is more lenient and masks this — `tsc` output is strict. The bug only surfaces in production Docker builds, which is why it wasn't caught earlier.

## 2. Prisma Generate vs Migrate — TypeScript Types Not Updating

**Symptom:**
After adding `correlationId` to `schema.prisma` and running `prisma migrate dev`, TypeScript still threw:

```
Object literal may only specify known properties, and 'correlationId' does not exist in type
'EventUncheckedCreateInput'
```

**Root cause:**
`prisma migrate dev` applies SQL to the database and writes a migration file. It does NOT regenerate the TypeScript client types in `node_modules/@prisma/client`. The types are generated by a separate step.

**Fix:**

```bash
npm run generate -w @eventflow/db   # regenerates @prisma/client types
npm run build -w @eventflow/db      # recompiles the db package
npm run build -w @eventflow/worker  # recompiles worker which imports the types
```

**Lesson:**
Two independent operations, two independent concerns:

- `prisma migrate` → changes the **database schema**
- `prisma generate` → changes the **TypeScript types your code sees**

Running migrate without generate leaves the database ahead of the type system. Always run both.

## 3. Auth Cache Bug — Parsing the Cache Key Instead of the Value

**Symptom:**

```json
{"error":"auth DB lookup failed","msg":"Unexpected token 'a', \"apikey:cac\"... is not valid JSON"}
```

Every POST request returned 500 Internal Server Error immediately after implementing Redis caching.

**Root cause:**
A one-character variable name mistake in the auth middleware:

```typescript
// wrong — parses the Redis KEY string, not the value
const record: CachedApiKey = JSON.parse(cacheKey);

// correct — parses the VALUE retrieved from Redis
const record: CachedApiKey = JSON.parse(cached);
```

`cacheKey` is the string `"apikey:cache:abc123..."` (the Redis lookup key). `cached` is the JSON value stored at that key. Passing `cacheKey` to `JSON.parse` tried to parse a Redis key string as JSON, which starts with `"apikey:cac"` — not valid JSON.

**Fix:**
Change `JSON.parse(cacheKey)` to `JSON.parse(cached)`.

**Lesson:**
Cache implementations have two distinct variables at every read — the key and the value. Using the wrong one is a silent logic error that only manifests at runtime. Fix required flushing the corrupted Redis cache (`FLUSHALL`) after correcting the code to clear any entries written by the broken version.

## 4. Swagger Spec Route Intercepted by `swaggerUi.serve`

**Symptom:**
`curl -s http://localhost:3000/api/v1/docs/spec` returned Swagger UI HTML instead of JSON.

**Root cause:**
Express middleware is executed in registration order. `swaggerUi.serve` was registered as a catch-all under `/api/v1/docs` before the specific `GET /api/v1/docs/spec` route. Every request to any sub-path under `/api/v1/docs` — including `/spec` — was intercepted and served the UI HTML.

**Fix:**
Register the specific route BEFORE the wildcard middleware:

```typescript
// spec route first — specific before general
app.get("/api/v1/docs/spec", (_, res) => res.json(swaggerSpec));

// swagger UI catch-all after
app.use("/api/v1/docs", swaggerUi.serve, swaggerUi.setup(swaggerSpec, { ... }));
```

**Lesson:**
Express matches routes in registration order. Specific routes must always come before middleware that handles a prefix broadly. This is the same reason `app.use("/api/v1", router)` with a catch-all inside the router would swallow all sub-routes if not ordered correctly.

## 5. Swagger Annotations Not Scanned — "No operations defined in spec"

**Symptom:**
Swagger UI loaded with correct schemas but showed "No operations defined in spec!" — none of the `@openapi` JSDoc annotations from route files were being picked up.

**Root cause:**
`swagger-jsdoc` resolves the `apis` glob pattern relative to `process.cwd()` (the directory Node.js was started from), not relative to the config file. The monorepo is started from the root (`npm run dev:api` from `/3-eventFlow/`), so `"./src/routes/*.ts"` resolved to `/3-eventFlow/src/routes/*.ts` — which does not exist. The actual route files are at `/3-eventFlow/app/api/src/routes/*.ts`.

**Fix:**
Use `__dirname` to build an absolute path that is always correct regardless of where the process starts:

```typescript
import { fileURLToPath } from "url";
import { dirname, join } from "path";

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

const options = {
  apis: [
    join(__dirname, "../routes/*.ts"),  // always resolves correctly
    join(__dirname, "../routes/*.js"),
  ],
};
```

**Lesson:**
Relative paths in configuration files are relative to `cwd`, not to the file containing them. In monorepos where scripts are run from the root, this consistently breaks tools that scan the filesystem. Absolute paths via `__dirname` (or `import.meta.url` in ESM) are always safer.

## 6. Race Condition Test Giving False Results — Rate Limit Masking the Test

**Symptom:**
The idempotency race condition test (10 concurrent POSTs with the same `idempotencyKey`) showed `0 × 2xx` responses, and the verification query returned a jq parse error instead of a count.

**Root cause:**
The test was run immediately after the rate limiting load tests (Tests 1 and 2) using the same API key. The sliding window rate limiter remembered the ~105k requests from the previous tests — the 100/min quota was still exhausted. Every request in the race condition test was rejected at the rate limit middleware, never reaching the events handler at all. The verification `curl` also got a 429 response (a JSON string, not an array), and jq failed trying to run array operations on a string.

**Fix:**
Provision a fresh API key with no rate limit history before running the race condition test:

```bash
curl -s -X POST $BASE/admin/tenants \
  -H "x-admin-secret: $ADMIN_SECRET" \
  -H "content-type: application/json" \
  -d '{"tenantId": "tenant-race-test"}' | jq '.rawAPiKey'

export API_KEY3="ep_live..."
```

Then run the test with `$API_KEY3`. Result: exactly 1 row in the database confirming the P2002 race handling works correctly.

**Lesson:**
Load tests pollute rate limit state for the API key used. Test isolation is not just about database state — it includes Redis state (rate limit windows, cache entries). When tests interact with shared infrastructure, always use isolated credentials per test.

## 7. Seed Container Failing — Wrong File Extension in Command

**Symptom:**

```
service "seed" didn't complete successfully: exit 1
docker compose logs seed → [no such service error or node crash]
```

**Root cause:**
The seed service command in `docker-compose.yml` was:

```yaml
command: sh -c "node packages/db/dist/seed.ts"
```

Two problems: `node` cannot execute `.ts` files directly, and the compiled TypeScript output is `.js` not `.ts`. Node looked for `seed.ts` in `dist/`, which does not exist — the compiler outputs `seed.js`.

**Fix:**

```yaml
command: sh -c "node packages/db/dist/seed.js"
```

**Lesson:**
Docker compose commands bypass the TypeScript toolchain entirely — they run compiled output directly via Node. The `dist/` directory only contains `.js` files. Using `.ts` extensions in run commands is a category error: TypeScript is a compile-time tool, not a runtime one (unless using `tsx`/`ts-node`, which are not present in production images).

## 8. `docker compose logs <container_name>` vs `logs <service_name>`

**Symptom:**

```
docker compose logs eventflow_seed
no such service: eventflow_seed
```

**Root cause:**
`docker compose logs` takes the **service name** as defined in `docker-compose.yml`, not the **container name** from `container_name:`. `eventflow_seed` is the container name; `seed` is the service name.

**Fix:**

```bash
docker compose logs seed       # correct — service name
docker compose logs eventflow_seed  # wrong — container name
```

**Lesson:**
Docker Compose and the Docker CLI operate on different namespaces. `docker logs eventflow_seed` (Docker CLI) uses container names. `docker compose logs seed` (Compose CLI) uses service names. Mixing them up is a common source of "not found" errors.

## 9. `localhost` vs Docker Service Hostname for DB Connections

**Symptom:**

```
Error: P1001: Can't reach database server at `localhost:5432`
```

when running `npm run migrate -w @eventflow/db` with all containers running.

**Root cause:**
Two different execution contexts require two different connection strings:

| Context | Who runs it | Correct hostname |
|---|---|---|
| `npm run migrate` (host machine) | Your laptop, outside Docker | `localhost:5432` |
| `docker compose` services | Inside Docker network | `postgres:5432` |

The `.env` file has `DATABASE_URL=...@localhost:5432` — correct for host-machine tools. Docker Compose overrides this with `DATABASE_URL=...@postgres:5432` for containers. The error appeared because the postgres container was not running — it had stopped/crashed and was not visible in `docker compose ps` output.

**Fix:**

```bash
docker compose ps -a              # show ALL containers including stopped ones
docker compose logs postgres      # check why postgres stopped
docker compose up -d postgres redis  # restart it
npm run migrate -w @eventflow/db  # retry
```

**Lesson:**
`localhost` inside a Docker container refers to that container itself, not the host machine. Docker's internal DNS resolves service names (`postgres`, `redis`, `api`) to container IPs within the same network. These two hostname contexts are completely independent and serve different audiences.

## 10. Negative Caching — Why Cache the "No" Answer

**The question:** If an API key is revoked (invalid), why write anything to Redis? Why not just return 401 directly?

**The problem without negative caching:**
A client with a leaked-then-revoked key that keeps retrying hits Postgres on every single request — permanently. The cache only stores "yes, this key is valid" entries, so every "no" answer requires a full DB lookup. At high request rates, this is indistinguishable from a targeted DB attack.

**The solution — cache the negative result too:**

```typescript
if (keyRecord && !keyRecord.active) {
  // cache {active: false} for 60s
  // next 10,000 requests with this key → Redis hit → 401, Postgres never touched
  await redis.set(cacheKey, JSON.stringify({ active: false, ... }), "EX", 60);
}
```

**The tradeoff documented:**
A genuinely revoked key stays "cached as invalid" for up to 60 seconds. If an admin activates a key, it takes up to 60 seconds to propagate. This is an acceptable operational tradeoff for the protection it provides.

**Lesson:**
Caching is not just for positive answers. The most expensive cache miss pattern is a high-frequency "this thing doesn't exist / isn't valid" check — negative caching converts it from O(n DB queries) to O(1 Redis lookup + n-1 cache hits).
